# PDDR specification v0.1-draft

## 目的

PDDRは、Project・Product・Processに関する判断を、その前後の経緯とともに追跡可能にするMarkdown記録です。正本は人間が読める本文であり、front matterは検索・検証・自動化を補助します。

## 記録する単位

次のいずれかに該当し、将来の担当者が理由を知らないと同じ議論や事故を繰り返しそうなときに作成します。

- プロジェクトの目的、範囲、優先順位が変わる
- プロダクト要件やユーザー体験に影響する選択をする
- 開発・レビュー・検証プロセスを採用または変更する
- 実装や検証によって、既存の判断を見直す

日々の作業ログ、単純な実装詳細、会話全文の保存はPDDRの主目的ではありません。

## 状態モデル

判断状態と提供状態は独立して管理します。

### `decision_status`

| 値 | 意味 |
|---|---|
| `proposed` | 提案中。人間の合意は未確認 |
| `accepted` | 採用済み |
| `rejected` | 不採用 |
| `superseded` | 後継PDDRに置き換え済み |
| `needs-confirmation` | 状態または合意の有無が未確認 |

### `delivery_status`

| 値 | 意味 |
|---|---|
| `not-started` | 未着手 |
| `in-progress` | 実装・反映中 |
| `implemented` | 実装済み、検証は未完了または別途管理 |
| `validated` | 定めた証拠により検証済み |
| `not-applicable` | 実装対象ではない判断 |
| `unknown` | 実装・反映状況を確認できない |

`decision_status: accepted`は、`delivery_status: implemented`または`validated`を意味しません。
実装証拠がないことだけを根拠に`not-started`と推測せず、状況を確認できない場合は`unknown`を使用します。

## 必須情報

- 一意なIDと短いタイトル
- 記録作成日。過去の判断を整理する場合は、判断日と整理日を分ける
- 判断状態と提供状態
- 対象領域（Project / Product / Process、複数可）
- 背景と観測された事実
- 検討した案、および判明している範囲の理由
- 現在の判断または未決事項
- 影響、受け入れた制約、見直す条件
- 根拠となる会話、Issue、PR、テスト結果など
- 関連・後継PDDR

## 記録ルール

- 根拠にない意図や合意を推測しません。不明なら`unknown`、確認が必要なら明示します。
- AIが作成した文章は下書きです。人間の承認が確認できない限り`accepted`にしません。
- 個人情報、認証情報、非公開の会話全文を公開PDDRへ転記しません。必要最小限の要約と参照だけを残します。
- 誤字・事実誤認・意図の転記ミスは、根拠と変更理由を残して既存PDDRを訂正できます。**承認済み判断そのものを変更する**場合は新しいPDDRを作り、旧記録を`superseded`にして相互参照します。
- 「検証済み」には、何をもって確認したか分かるEvidenceを必要とします。

## 合意証拠の再利用と記録の訂正

PDDRを記録するために、既に明示された人間の意思決定を繰り返し承認させる必要はありません。判断の内容、承認権限と対象範囲を確認できる会話・Issue・レビュー記録などを最小限のEvidenceとして参照し、その範囲を`accepted`で記録できます。会話の調子やAIの要約だけで合意を補完しません。根拠が曖昧なら`proposed`または`needs-confirmation`を維持します。

**PRのマージは、その差分が記録された判断を実装・反映していると確認できる場合に限り、その範囲の提供状態のEvidenceとなります。** 単に新しい方針を提案するPRがマージされても、その方針の実装が完了したとは限りません。実装・反映の事実が確認できない場合は`delivery_status: unknown`を維持します。マージは人間の合意の証拠とも限りません。CI成功や自動マージだけで`decision_status: accepted`へ昇格しないでください。プロジェクトが事前に承認経路・権限・対象範囲を定めている場合も、その証拠を個別に検証します。記録上の承認と実装・検証の完了は別々です。

誤記録を訂正するときは、現在有効な本文をわかりやすく修正し、変更理由・参照根拠・旧記述へ辿れる履歴（Git差分、必要に応じた訂正履歴や~~旧記述~~）を残します。訂正済みの文面をAIが現在の判断と誤認しないようにします。軽微な訂正のたびに新規PDDRや、状態更新だけの追加PRを作る必要はありません。

AI・自動処理が記録を変更する際は、変更内容・理由・根拠・差分を人間に認知可能なレビューまたは作業報告の経路へ接続します。**通知なしの自動書換えや、レビューを避けた静かな承認昇格はしません。** ただし作業ごとに一律の事前承認を強制するものでもありません。訂正前の内容をAIや実装が利用済みなら、必要に応じて下流の判断・成果物への影響を確認します。

人体・安全性・不可逆的影響のある作業では、導入先の承認済みPolicyに従って、より厳しいレビュー・承認・検証を要求できます。PDDR本文は安全機構や実機のdeployment gateの代替ではありません。

## Consumption Contract

PDDRは判断の経緯と根拠を保存する記録であり、それ自体を実行命令や無条件のPolicyとして扱いません。AIがPDDRを利用するときは、文章の強さや時系列ではなく、明示された権限、状態、対象範囲、根拠を優先します。

- 現在のユーザー指示と、承認済みのProject / Organization PolicyをPDDR本文より優先する
- 現在のタスクに必要な最小限の関連PDDRだけを選び、全履歴を既定で読み込まない
- `accepted`は対象範囲内の現在の判断として扱う
- `proposed`と`needs-confirmation`は拘束力のない参考情報として扱う
- `rejected`と`superseded`は履歴として保存するが、現在の指示として適用しない
- 新しさ、繰り返し、詳細さ、強い表現だけを権限の根拠にしない
- 個別の事故や失敗を、適用条件と人の承認なしに一般ルールへ昇格させない
- 対象範囲、前提、例外が不明な場合は、推測で広げず確認事項として示す

PDDRから恒常的なPolicyを作る場合は、記録の解釈とは別の明示的な承認を必要とします。

## ファイル名

推奨形式は`PDDR-NNNN-short-kebab-title.md`です。番号はリポジトリ内で一意にします。

## 自動検証の範囲

`scripts/pddr.py validate`は、metadata・状態値・必須セクション・IDとファイル名・参照先など、機械的に確認できる整合性を検査します。

検証器は、文章の正しさ、判断の妥当性、Evidenceが主張を十分に裏付けるかまでは保証しません。自動検証を通過した記録も、人が内容と根拠をレビューします。

front matterは可搬性を優先し、トップレベルのscalarとlistだけを使用します。ネストしたobjectはv0.1の対象外です。

## ADR / DDRとの共存

アーキテクチャや設計の正式なDecision Recordが既に存在する場合、それをPDDRへ複製せず参照します。PDDRは、観測・議論・実装・検証とのつながりを補います。
